## 已知产品现状

Narraverse2.0 当前已经拥有多块有价值能力，但它们并没有完全收口到同一套数据和运行逻辑中。

当前重点包括：
- 总资料库 / Master Library；
- 角色与设定资料；
- 写作能力；
- 游戏模式；
- 叙界；
- 叙界内文字冒险；
- Module4 / 自由沙盒；
- 本地翻译与 8097 Bridge；
- 模型网关与多模型接入；
- Agent 体系。

## 当前决策（经独立复核后更新）

路线尚未锁定。SYSTEM MAP 已完成，独立复核已完成。

候选路线：
- **A+（共享数据/事实层 + 独立运行时）**：Master Library 为唯一资料真源 + 新增统一世界事实/Canon 服务 + 模型网关保持统一 + 三套运行时独立但状态变更经统一事实服务落库。新增候选，风险最低。
- **B（保留资产，重构核心）**：以 Master Library 为统一资料层 + Game 事件溯源/预设/Actor State 为统一运行时内核 + 模型网关为统一调用层。**已降级为"首选验证假设"，非推荐路线**——核心可行性（状态 schema 兼容、预设覆盖度、存档迁移成本）尚未验证。
- **C（近乎重写 + 资产迁移）**：迁移有价值的数据、规则、算法到干净架构。需基于重写成本 vs 长期维护收益重新评估，不再等同于"丢弃资产"。

路线锁定前置条件：状态 schema 字段级映射证明完成、A+/B/C 三路线量化成本对比、存档迁移方案可行、第二次独立复核无异议。

## 一级产品目标（新增）

**统一 Canon/事实采纳层**：运行时产生的世界事实（角色关系变化、地点状态、事件结果、时间线推进）必须能被采纳为世界 Canon，有来源、时间戳、可见性、可回滚。写作草稿、冒险状态、Module4 facts 都通过统一 Canon 服务提交候选，经确认后生效。这是所有路线的共同必选项，不依赖运行时统一。

## 当前最重要的问题

不是"模块数量太多"本身，而是要确认：
- 同一种角色/世界信息是否被多套系统重复表示；
- 游戏模式、文字冒险、自由沙盒是否各自维护运行状态；
- 三套玩法是否重复实现导演、状态、事件、行动判断等能力；
- 写作与互动运行时是否真正读取同一套世界资料；
- 总资料库与具体世界资料库之间的数据继承和版本关系是否足够清晰；
- **运行时产生的世界事实能否跨系统采纳为 Canon（新增，当前无机制）。**

## 已知叙界嵌入问题

叙界当前通过持久 iframe 嵌入 Denova。现有桥接主要同步主题、语言、可见性和 Module4 打开/关闭等有限信息。

这不代表 iframe 必须马上删除，但说明当前"看起来在一起"和"真正共享同一上下文"不是一回事。

## Module4 当前理解

Module4 已经包含较完整的世界运行/模拟流程，例如预演、行动、相遇、判断、事实、日志、日结等。

现阶段需要重点确认这些能力是否应该下沉到统一互动运行时，而不是继续作为独立玩法系统存在。独立复核指出：Module4 的时钟/日程/跨日结算是自主时间推进循环，可能需要核心运行时扩展，而非仅作为 Game 预设。
