# Narraverse 总体重规划目标

## 一句话目标

把 Narraverse2.0 从“多个相互嵌套、各自维护状态的模块”，整理成一条统一产品链：

`资料导入 → 总资料库 → 具体世界 → 写作 / 统一互动运行时 → 世界状态与事实 → 审核与采纳`

## 1. 上游：资料整理

需要统一处理：
- 角色卡；
- 设定卡；
- 世界书；
- 地点、势力、物品、技能、规则等设定；
- 外部文档和已有数据库内容。

目标能力：
- 导入；
- 解析；
- 翻译；
- 字段整理；
- 去重；
- 版本管理；
- 来源追踪；
- 冲突识别。

## 2. 总资料库

总资料库保存相对稳定、可复用、可追溯的“母版资料”。

它不应该直接承受某一次冒险中的受伤、关系变化、剧情成长等运行时状态。

## 3. 具体世界资料库

每个具体世界拥有自己的资料与状态。

资料可以来自总资料库，但进入世界后需要支持：
- 世界专属覆盖；
- 独立版本；
- 独立关系；
- 独立时间线；
- 独立角色成长和状态；
- 不污染其他世界和总资料库。

## 4. 写作

写作不应成为资料孤岛。

它应该读取同一个世界资料、角色、地点、设定和已采纳事实，但写作草稿与世界运行实验不能自动成为正式世界事实。

后续需要研究：
- 草稿；
- 分支；
- 快照；
- canon / non-canon；
- 从写作结果中“采纳”事实；
- 从运行结果中“采纳”事实。

## 5. 统一互动运行时

重点研究现有三套能力：
- 游戏模式；
- 叙界文字冒险；
- 自由沙盒 / Module4。

不要先假定它们必须保留为三套产品。

优先验证能否收敛为同一个运行核心，然后通过不同预设形成不同玩法，例如：
- 剧情型；
- 文字冒险型；
- TRPG 型；
- 自由沙盒型；
- 世界模拟型；
- 开发测试型。

## 6. 现有游戏方案预设是重点资产

必须调查现有游戏模式中的：
- 故事导演；
- 叙事风格；
- 状态系统；
- TRPG 检定；
- 事件包；
- 其他方案/预设能力。

核心问题是：这些是否已经足以成为统一运行时的“配置层”。

如果答案是肯定的，就不应再维护三套相似玩法引擎。

## 7. 叙界重新定位候选

叙界更可能适合作为：
- 世界管理中心；
- 角色与设定浏览中心；
- 关系与时间线查看；
- 冒险/故事档案管理；
- 从任意上下文启动写作或运行时。

而不是再自己维护一套独立文字冒险核心。

## 8. 技术路线不设死

研究不能被现有 Go + React + Python + iframe 架构绑住。

最终允许比较三条路线：

### A. 渐进整合
在现有平台上继续改，尽量复用现有模块。

### B. 保留资产，重构核心
保留有价值的数据、业务能力和部分 UI，但重做统一数据层、世界模型和互动运行时。

### C. 近乎重写
只迁移有价值的数据、规则、算法和少量成熟代码，重新设计产品和核心技术架构。

最终要基于真实代码给出推荐，不准因为“重写比较爽”就重写，也不准因为“已经写了很多”就继续背历史包袱。

## 9. 当前阶段

现在先不执行大重构。

第一阶段只建立真实系统地图：
- 哪些数据模型重复；
- 哪些状态重复；
- 哪些 API 重复；
- 三种互动玩法共享什么；
- 三者真正不同的是什么；
- 哪些现有代码值得保留。

完成 SYSTEM MAP 后再决定路线 A / B / C。
