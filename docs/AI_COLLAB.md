# Narraverse 多 AI 协作与交接规则 v1

## 目标

让 Workbuddy、Codex、豆包在额度不对称的情况下协作，同时尽量减少用户手工判断和重复说明。

## 当前额度策略

### Workbuddy
额度较多，作为默认主力。

优先给它：
- 大规模阅读；
- 搜索；
- 代码地图；
- 普通实现；
- 测试；
- 构建；
- 文档整理；
- 迁移前置工作；
- 小中型重构。

### Codex
额度少，作为高价值工程执行者。

只在以下情况使用：
- 核心架构落地；
- 跨模块复杂修改；
- 高难 bug；
- 状态一致性、并发、迁移、复杂重构；
- Workbuddy 已完成调查，但实现明显超出它的可靠范围。

### 豆包
额度少，作为第二意见与产品/架构复核。

只在以下情况使用：
- 重大产品方向选择；
- 方案存在明显争议；
- 需要独立视角复核；
- 重要架构决策前做反方检查。

## 用户参与规则

不要让用户自己维护复杂的 AI 工作流。

如果当前 AI 做完后需要换人，交接必须明确写：

> 下一步：把下面这段内容发给 Workbuddy / Codex / 豆包。
> 目的：……
> 它完成后，请把 …… 带回来。

如果无需换 AI，也要明确说明继续由谁执行。

## 任务流

标准流程：

`TASK → 执行 → 验证 → HANDOFF → 下一 TASK`

每个任务尽量只由一个主执行者负责。

多个 AI 可以分析同一个问题，但不要同时修改同一份正式代码。

## 仓库职责

### Narraverse-Orchestrator
只放：
- 任务；
- 计划；
- 架构决策；
- 研究报告；
- HANDOFF；
- 给 AI 的提示词。

### Narraverse2.0
只放真正产品需要的正式代码、正式文档、测试和迁移。

## 分支和 PR

用户目前不需要熟练掌握 Git 分支和 PR。

AI 执行者需要自己处理这些技术细节，并在交接中用大白话说明结果。

最简原则：
- 不直接在重要主干上做大规模未验证改动；
- 一个高风险任务尽量一个独立分支；
- 做完测试后再合并；
- 用户无需手工记 Git 命令。
