# Narraverse 多 AI 协作与交接规则 v2

## 目标

让 Workbuddy、豆包、Codex 在额度和能力不对称的情况下协作，同时尽量减少用户手工判断和重复说明。

## 当前额度策略

### Workbuddy
额度较多，是主力执行者之一，偏本地工程执行。

优先给它：
- 本地仓库调查；
- 大规模阅读和搜索；
- 普通实现；
- 测试；
- 构建；
- 环境操作；
- 迁移前置工作；
- 小中型重构；
- HANDOFF 整理。

### 豆包
当前额度也较多，甚至可能高于 Workbuddy，同样作为主力执行者。

不再限制为“只做第二意见”。优先给它：
- 大规模代码/文档研究；
- 架构分析；
- 系统对照；
- 产品和流程设计；
- 重构方案；
- 文档整理；
- 第二意见和反方复核；
- 在具备所需访问和执行能力时，承担普通调查、实现和验证。

Workbuddy 与豆包的任务分配原则不是“谁额度更省”，而是：
1. 谁更适合当前任务；
2. 谁已经掌握更多当前上下文；
3. 是否需要直接操作本地工程环境；
4. 是否会造成重复阅读和重复 token 消耗。

### Codex
额度少，作为高价值工程执行者。

只在以下情况优先使用：
- 核心架构落地；
- 跨模块复杂修改；
- 高难 bug；
- 状态一致性、并发、迁移、复杂重构；
- Workbuddy / 豆包已经完成调查和方案，但具体实现明显需要更强代码能力。

不要让 Codex 承担可以由豆包或 Workbuddy 完成的大规模机械阅读、重复测试和普通整理。

## 用户参与规则

不要让用户自己维护复杂的 AI 工作流。

如果当前 AI 做完后需要换人，交接必须明确写：

> 下一步：把下面这段内容发给 Workbuddy / 豆包 / Codex。
> 目的：……
> 它完成后，请把 …… 带回来。

如果无需换 AI，也要明确说明继续由谁执行。

## 任务流

标准流程：

`TASK → 执行 → 验证 → HANDOFF → 下一 TASK`

每个任务尽量只由一个主执行者负责。

多个 AI 可以分析同一个问题，但不要同时修改同一份正式代码。

对于重要架构决策，可以采用：

`主研究者（豆包或 Workbuddy） → 另一主力做独立复核 → 必要时 Codex 做实现风险检查`

但不要默认每个任务都三 AI 齐上，否则协作仓库会迅速进化成人类最爱的东西：会议系统。

## 仓库职责

### Narraverse-Orchestrator
只放：
- 任务；
- 计划；
- 架构决策；
- 研究报告；
- HANDOFF；
- 给 AI 的提示词。

### Narraverse2.0
只放真正产品需要的正式代码、正式文档、测试和迁移。

## 源码调查身份确认

调查 Narraverse2.0 当前实现前，必须记录并确认：
- 仓库：`llys-p/Narraverse2.0`
- branch
- commit SHA
- 实际工作目录

旧版 `E:\Narraverse` 不得作为 Narraverse2.0 当前实现的事实来源。需要历史比较时必须另开历史对比任务。

## 分支和 PR

用户目前不需要熟练掌握 Git 分支和 PR。

AI 执行者需要自己处理这些技术细节，并在交接中用大白话说明结果。

最简原则：
- 不直接在重要主干上做大规模未验证改动；
- 一个高风险任务尽量一个独立分支；
- 做完测试后再合并；
- 用户无需手工记 Git 命令。
