## 一、支持的结论

以下结论我认为证据充分、判断合理，应予保留：

### 1. 碎片化诊断成立
SYSTEM_MAP 对"同一角色/条目 3–5 库并存""三套状态机 schema 不兼容""双模型调用路径 + 双 lore 入口 + 4 条同步线"的诊断，均附有具体文件路径、函数名与行号，证据链完整。§H 对"正常分层"与"割裂候选"的区分是严谨的，没有把所有差异都误判为问题。

### 2. Master Library 是高价值资产
`internal/book/master_library*.go` 的原件/活动版分离、sha256 内容去重、翻译版本树、CAS 冲突校验、历史归档、tombstone、实例化/重投影——这是全项目最接近"统一资料母版"的成熟架构，且设计质量明显高于其他模块。作为任何路线的资料层骨架都是正确选择。

### 3. 模型网关已实现实质收敛
`model_gateway.go` 把 writing/game/narraverse/module4 全部映射到 `interactive_story` / `ide` Agent kind，这是真实存在的统一调用层，不是规划。它为"统一运行时"提供了已落地的基础设施证据。

### 4. Game 模式是运行时内核最完整的一套
事件溯源 JSONL + Actor State（schema 冻结 + typed ops）+ d20 检定引擎 + 导演规划器 + 预设加载器体系（版本化 JSON Library + 组合 + disabled + resolved snapshot）——这套能力的完整度确实高于叙界和 Module4。作为统一内核候选是有依据的。

### 5. 报告对自身局限的诚实声明值得肯定
Provenance 段（commit SHA、浅克隆 depth 1、生成物不在克隆内、未使用旧目录）、§11 的 8 项待确认清单、"本报告不锁定路线"的声明——这些是高质量工程文档的标志，不应在后续迭代中丢失。

### 6. 叙界重新定位为"世界管理/浏览/档案中心"方向合理
MASTER_PLAN §7 提出叙界不再维护独立文字冒险核心，而是作为世界管理与档案入口——这与"叙界 UI 成熟、角色卡解析管线完善"的证据一致，是合理的产品收敛方向。

## 二、不支持的结论

以下结论我认为证据不足、逻辑跳跃或前提未经验证，需要修正或降级：

### 1. 路线 B 被推荐得比证据支持的更强
SYSTEM_MAP 正文谨慎地写了"初步更支持 B""本报告不锁定路线"，但 HANDOFF-001 的"关键结论"第 4 条和"下一步建议"实际上把 B 当作既定方向来组织后续工作（"以 Master Library 为统一资料层 + Game 内核为统一运行时"）。

**问题**：路线 B 的核心可行性——Game 的事件溯源 + Actor State 能否无损承载叙界 8 标签协议和 Module4 facts（含 knownTo/epistemicStatus）——在 §11 第 2 项被明确列为"待确认"。在中心可行性未验证前就把 B 作为推荐路线，逻辑上倒置了。

**修正**：路线 B 应定位为"待原型验证的首选假设"，而非"推荐路线"。TASK-002 的产出应能**证伪** B，而不是只为 B 铺路。

### 2. "统一为一个 World Runtime"是未加审查的前提
MASTER_PLAN 和 SYSTEM_MAP 都默认目标是"三套玩法收敛为一个运行时核心"，但从未论证**为什么必须是一个而不是两个**。

三套系统的交互范式有本质差异：
- **Game 模式**：回合制、导演驱动、结构化（prepare_turn → submit_turn）、事件溯源；
- **叙界文字冒险**：自由对话、模型驱动状态变更、无导演、无世界时钟；
- **Module4**：时间驱动模拟（时钟自主推进、NPC 日程、跨日结算）、确定性规则优先、AI 仅负责叙事续写。

把时间驱动模拟塞进回合制事件溯源引擎，和把自由对话塞进结构化回合协议，都是高成本的抽象拉伸。**"统一数据/事实层"的价值远清晰于"统一运行时"**——前者解决真源不唯一，后者可能只是为了统一而统一。

**修正**：将目标从"一个 World Runtime"改为"统一数据/事实层 + 可插拔运行时（可能是两个：回合制事件溯源内核承载 Game+叙界，时间驱动模拟内核承载 Module4）"。在 TASK-002 中增加"1 个 vs 2 个运行时"的明确对比。

### 3. "Preset（预设）"抽象对 Module4 被过度拉伸
SYSTEM_MAP §10 把 Module4 的时钟/日程/跨日结算称为"世界模拟预设"，§9 第 2 条又承认 Game 预设"未覆盖"这些能力。这里存在概念矛盾：

- Game 现有预设（故事导演、叙事风格、TRPG 检定、事件包、Actor State）都是**回合制故事**的配置项，通过 `StoryDirectorModuleRefs` 组合，在 `prepare_interactive_turn` / `submit_interactive_turn` 的回合管线中消费；
- Module4 的时钟（3 时段 × 3 tick）、NPC 日程 slot、evening 结算（settlement.js）是**自主时间推进循环**，不依赖玩家回合触发。它不是"配置"，而是**运行时调度机制**。

把调度机制叫做"预设"，掩盖了它需要核心运行时支持（时钟循环、日程执行器、结算触发器）的事实。如果这些只能靠"预设"实现，那预设系统本身需要被大幅扩展，扩展后的它就不再是 Game 现有的轻量配置层了。

**修正**：将 Module4 的时钟/日程/结算明确列为"可能需要核心运行时扩展的能力"，与"纯配置预设"分开评估。在 TASK-002 中验证：这些能力能否作为 Game 内核的**扩展模块**（而非预设）接入，如果不能，路线 B 的"以 Game 为内核"前提就不成立。

### 4. 四大结构性问题清单遗漏了"Canon/事实采纳"这一核心产品缺口
SYSTEM_MAP §5/§6 列出了数据模型分裂、世界状态分裂、多运行时重复、API/Agent 重复，但没有把"**写作草稿 / 冒险状态 / Module4 facts 无法跨系统采纳为世界 Canon**"列为一级问题。

MASTER_PLAN §4 提到了 canon/non-canon 和"从写作/运行结果中采纳事实"，但 SYSTEM_MAP 的问题清单没有把它上升为结构性问题。实际上：
- 叙界无 adopt/canon 机制（SYSTEM_MAP D 节已确认）；
- Module4 facts 有 visibility/knownTo/epistemicStatus，但只在 Module4 内部有效；
- Game 的"稳定设定才写 lore"靠流程纪律而非机制强制；
- Master Library 的 `create_master_proposal` + UI 确认是唯一的采纳机制，但只覆盖资料层，不覆盖运行时产生的世界事实。

一个创意叙事平台的核心价值是"故事/世界积累可复用的真相"，当前系统在这一点上是空白的。这比"三套状态机 schema 不同"更接近产品本质问题。

**修正**：在结构性问题清单中增加"无跨系统 Canon/事实采纳机制"，并在任何路线的目标中明确"统一事实采纳层"是必选项。

### 5. 路线 A 被过快否定
SYSTEM_MAP §10 对 A 的否定只有一句："A（渐进整合）只能缓解、不能根治三大结构性问题——补丁成本会持续累积。"这是断言而非论证。

存在一种 **A+（共享数据/事实层 + 独立运行时）** 路线未被明确考虑：
- 以 Master Library 为唯一资料真源（已具备）；
- 新增统一的"世界事实/Canon 服务"（可基于 Master Library 的 proposal 机制扩展），三套运行时都通过它读写世界事实；
- 模型网关已统一，保持不变；
- 三套运行时各自保留，但状态变更必须经过统一事实服务落库；
- 逐步把重复的 lore 入口、同步线向 Master/sync-adventure 收敛。

这条路线的风险远低于 B（不重写运行时、不迁移状态 schema、不破坏现有存档），且能解决"真源不唯一"和"事实无法采纳"两个最核心的问题。它不能解决"三套状态机重复实现"，但如果三套交互范式本就不同，重复实现未必是需要根治的病。

**修正**：将 A+ 作为明确的第三候选（与 A、B、C 并列或替代 A），在 TASK-002 中要求对 A+ / B / C 做同等深度的成本-收益对比。

### 6. 路线 C 被"丢弃资产"稻草人化
SYSTEM_MAP §10 对 C 的否定是"会丢弃高价值资产：Master Library、Game 预设体系、事件溯源内核、叙界提示词管线与测试网"。但 C（近乎重写）的定义本身就是"只迁移有价值的数据、规则、算法和少量成熟代码，重新设计产品和核心技术架构"（MASTER_PLAN §8）——它**不要求丢弃资产**，而是要求迁移资产到新架构。

把 C 等同于"丢弃资产"是稻草人论证。C 的真实代价是平台重写的工程成本和迁移风险，而非资产丢失。报告没有评估 C 的长期收益（干净架构、无历史包袱、可针对统一数据/事实层从头设计）与 B 的"在 Game 现有代码上重构核心"可能继承的 Game 自身技术债。

**修正**：对 C 的评估应基于"重写成本 vs 长期维护收益 + 迁移可行性"，而非"是否丢弃资产"。要求 TASK-002 对 C 做至少与 B 同等深度的评估。

### 7. 浅克隆（depth 1）限制了对"资产是否值得保留"的判断
SYSTEM_MAP 的所有"可复用资产"判断（§7）都基于当前快照的代码质量，没有历史维度。但"是否值得保留"不仅取决于代码现在写得好不好，还取决于：
- 该模块的变更频率（高频变更的模块技术债累积快）；
- bug 修复历史（是否反复修同一类问题，暗示架构缺陷）；
- 贡献者与评审质量；
- 与其他模块的耦合演化。

depth 1 克隆看不到这些，导致"保留 vs 重写"的判断缺少历史证据。

**修正**：TASK-002 必须使用非浅克隆（至少保留最近 3–6 个月历史），对 §7 列出的每项可复用资产补充"变更频率 + 缺陷密度 + 耦合演化"的历史评估。

## 三、风险点

### R1. 状态 schema 迁移是路线 B 最大的未量化风险
Actor State（Game）、8 标签 diff（叙界）、world schema v1.5（Module4）三者语义不兼容。路线 B 要求统一到 Actor State，但没有任何字段级映射证明、没有迁移脚本、没有回滚方案。现有用户存档（叙界 IndexedDB `adventureAI_db`、Module4 localStorage `narraverse:module4:state`、Game jsonl）在 schema 统一后如何处理，完全未涉及。这是可能导致用户数据丢失的高风险项。

### R2. Go/Python 同写 `.denova/projects` 无锁协调
SYSTEM_MAP §6 和 HANDOFF-001 都指出 Go 服务与 8097 Python 桥直接读写同一文件树，克隆内未见锁协调证据。这是真实的一致性风险（并发写入可能导致 lore 损坏或冲突丢失），且**任何路线都必须解决**——A/B/C 都没有给出方案。

### R3. "Preset 过度抽象"可能导致配置系统复杂度爆炸
如果按路线 B 把时钟/日程/结算、叙界 8 标签协议、World Info 注入都做成"预设"，预设系统将从 Game 现有的 6 类模块膨胀到 10+ 类，且各类预设的语义域完全不同（故事配置 vs 时间调度 vs 协议解析）。一个过度通用的预设系统往往比三套独立系统更难维护。

### R4. 双模型路径的运行时行为未实测
SYSTEM_MAP §11 第 4 项指出叙界 embedded 首轮是否强制本地 apiConfig 未验证。如果嵌入态仍会触发浏览器直连兜底，则"模型网关已统一"的结论在运行时层面不成立，路线 B 依赖的"统一调用层"前提需要修正。

### R5. TASK-002 范围过大，可能自身需要分解
§11 的 8 项待确认 + 本复核建议新增的（schema 映射证明、成本估算、存档迁移、非浅克隆历史评估、A+/C 同等评估、1 vs 2 运行时对比）合计 14+ 项，全部交给 Workbuddy 一个任务可能超出 5 小时窗口或单次执行的合理范围。

### R6. 路线 B 继承 Game 技术债的风险未评估
"以 Game 为内核"意味着新统一运行时建立在 Game 现有代码之上。Game 的事件溯源、Actor State、预设系统虽然完整，但也可能携带自身的设计约束和技术债（例如 `submit_interactive_turn` 的 oneOf 五类变更是否真的足够通用、Actor State schema 冻结机制是否支持热迁移）。报告没有评估"在 Game 上重构"vs"参考 Game 设计重写"的差异。

## 四、修改建议

### M1. 修正路线表述
将 HANDOFF-001 和 SYSTEM_MAP §10 中对路线 B 的表述从"初步更支持 / 推荐"统一改为：
> "路线 B（保留资产，重构核心）是当前**首选验证假设**。其核心可行性（状态 schema 兼容、预设覆盖度、存档迁移成本）尚未验证。TASK-002 的目标是**验证或证伪** B，同时对 A+（共享数据层 + 独立运行时）和 C（干净重写 + 资产迁移）做同等深度评估。路线锁定在 TASK-002 之后。"

### M2. 新增 A+ 路线为正式候选
在 MASTER_PLAN §8 和 SYSTEM_MAP §10 中，将原 A/B/C 三路线扩展为 A+ / B / C 三路线（A+ 替代原 A，或与 A 并列说明 A+ 是 A 的增强版）：
- **A+**：Master Library 为唯一资料真源 + 新增统一世界事实/Canon 服务 + 模型网关保持统一 + 三套运行时独立但状态变更经统一事实服务落库 + 逐步收敛重复 lore 入口与同步线。
- 明确 A+ 的不解决项：三套运行时仍独立实现、状态 schema 仍不统一。将"这是否可接受"作为开放问题。

### M3. 将"统一运行时"降级为"统一数据/事实层 + 可插拔运行时"
在 MASTER_PLAN 中，把目标从"统一互动运行时"修正为：
> "统一资料层（Master Library）+ 统一世界事实/Canon 层 + 统一模型/Agent 网关 + 可插拔运行时（回合制事件溯源内核 / 时间驱动模拟内核，数量待 TASK-002 验证为 1 或 2）。"

### M4. 新增"Canon/事实采纳"为一级产品目标
在 MASTER_PLAN 中新增独立章节（或在 §4 写作、§5 运行时之间），明确：
- 运行时产生的世界事实（角色关系变化、地点状态、事件结果、时间线推进）必须能被采纳为世界 Canon；
- Canon 有来源、时间戳、可见性、可回滚；
- 写作草稿、冒险状态、Module4 facts 都通过统一 Canon 服务提交候选，经确认后生效；
- Master Library 的 proposal 机制可作为 Canon 服务的实现参考。

### M5. 区分"纯配置预设"与"核心运行时扩展"
在 SYSTEM_MAP 中，对 Game 预设体系的评估增加分类：
- **纯配置预设**（可直接作为统一配置层）：叙事风格 Teller、图像方案、事件包内容、TRPG 规则集（d20/计分可切换）、故事导演参数；
- **核心数据模型**（不是配置，是运行时依赖）：Actor State schema（即使可冻结/可扩展，也是核心依赖）；
- **需要核心扩展的能力**（不是现有预设能覆盖的）：Module4 时钟/日程/跨日结算、叙界 World Info 关键词注入、叙界 8 标签协议解析。

### M6. 要求 TASK-002 使用非浅克隆并补充历史评估
TASK-002 的克隆深度至少保留最近 6 个月（或全历史），对 §7 每项可复用资产补充：
- 最近 6 个月 commit 数与变更文件范围；
- bug/修复类 commit 占比；
- 与其他模块的交叉修改频率（耦合演化）；
- 据此修正"保留 vs 重写"判断。

### M7. 新增存档迁移评估为路线锁定的前置条件
在任何路线被锁定前，必须产出：
- 现有三类存档的数据规模与格式分布（叙界 adventure 数量、Module4 world 数量、Game story 数量）；
- 目标 schema 的字段级映射表（含无法映射的字段）；
- 迁移脚本方案与回滚方案；
- 不可迁移数据的用户告知策略。

### M8. 分解 TASK-002
建议将原 TASK-002 拆为：
- **TASK-002a**（Workbuddy）：§11 第 1–4 项运行态验证 + 状态 schema 映射证明 + 非浅克隆历史评估；
- **TASK-002b**（Workbuddy 或豆包）：§11 第 5–8 项 + A+/B/C 成本估算 + 存档迁移评估 + 1 vs 2 运行时对比；
- 两任务完成后再进入路线锁定。

| 1 | SYSTEM_MAP 是否足够支持当前结论？ | 足够支持**诊断**（碎片化、重复确实存在），不足以支持**处方**（路线 B）。中心可行性问题（schema 兼容、预设覆盖、迁移成本）被列为待确认却仍推荐 B，逻辑倒置。 |
